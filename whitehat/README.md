# ARTEX · проверка достоверности

Модуль проверяет сохранённые доказательства по конкретному утверждению. Он работает отдельно от активных агентов ARTEX, на Python 3.10+ со стандартной библиотекой. В режиме по умолчанию не выполняются сетевые запросы, команды сканеров и код из находок. Можно обрабатывать архив на отдельной машине.

## Запуск

Из корня репозитория, в новый каталог для каждого результата:

```bash
python3 -m whitehat demo demo-input && python3 -m whitehat report demo-input/case.json --out demo-report
```

Открой `demo-report/report.html`. Машиночитаемый результат лежит рядом в `report.json`. Демо содержит синтетические снимки и показывает весь путь от файла до отчёта. Тесты запускаются командой `python3 -m unittest discover -s whitehat -t . -v`.

## Работа со своим аудитом

1. Укажи узкое утверждение, цель, эталон, версию и UTC-период наблюдений (Unix seconds). Для приватного объекта зафиксируй ожидаемые права двух тестовых пользователей до просмотра результата. Проверку после исправления веди как отдельный случай с новой версией.
2. В карточке находки ARTEX открой **Evidence verification → Download evidence ZIP**. Экспорт также доступен через **Findings → Export → Markdown ZIP**. Нужны исходные ZIP со связанным трафиком, а не текст пересказа. Для других адаптеров используются исходные XML/JSON. Положи файлы рядом с манифестом. У архива с исходным трафиком может быть чувствительное содержимое.
3. По примеру `demo-input/case.json` опиши запуски. Для каждого укажи реального сборщика, сторону `target` или `control`, версию, относительный путь и контрольную сумму SHA-256, полученную через доверенный канал при сборе. Если независимый запуск привязан к другой карточке ARTEX, укажи её строковый `finding_id` в соответствующем запуске. Хеш без доверенного источника подтверждает только внутреннюю согласованность.
4. Запусти `python3 -m whitehat report case.json --out report-001`. Статус относится только к наблюдавшейся версии, указанной цели и периоду. Права аккаунтов, независимость сборщиков и версию среды удостоверяет оператор. Файлы исходного трафика и секреты из HTTP-заголовков не копируются в итоговый отчёт. Значения, явно внесённые в поля цели и правила, отображаются в локальном отчёте. Используй тестовые идентификаторы.

### Правила прямой проверки

| Правило | Вход | Условие |
|---|---|---|
| `http.private_json` | Экспорт ARTEX с четырьмя типами записей в каждом сборе | Прямой GET /identity каждого пользователя устанавливает две разные личности. GET закрытого синтетического объекта владельцем содержит ожидаемую метку. Для второго пользователя проверяются та же метка и тот же URL. У исправного контроля владелец читает объект, а второй пользователь получает минимальный отказ 403/404. |
| `http.nosniff` | Экспорт ARTEX | Проверяется значение заголовка конкретного URL, метода GET и успешного ответа с заданным типом контента. Переадресация или HTML вместо ожидаемого JSON дают неопределённый результат. Это проверка конфигурации. |
| `tcp.exposure` | Полный Nmap XML, `rule.port` | Берётся явная запись ожидаемых IP, TCP и порта в завершённом сканировании. `open` и `closed` различимы. Отфильтрованный порт и отсутствие записи дают неопределённость. Утверждение ограничено точками наблюдения сборщиков. |
| `postgres.superuser` | JSON результата запроса к каталогу, `rule.role` | Проверяются имя БД, роль, время и булево значение `rolsuper`. Идентификатор экземпляра и маршрут получения файла должны быть проверены оператором. |

Для PostgreSQL можно сохранить вывод следующего запроса, выполненного владельцем стенда через `psql -XAt` с переменной `audit_role`. Поля `target/control` в этом профиле — разные имена тестовых БД. Учитывай, что роли разделяются на уровне кластера, и для эталона используй отдельный кластер.

```sql
SELECT json_build_object('database', current_database(), 'role', rolname,
       'captured_at', floor(extract(epoch FROM clock_timestamp()))::bigint,
       'rolsuper', rolsuper) FROM pg_catalog.pg_roles WHERE rolname = :'audit_role';
```

Для `http.private_json` в `rule` задай `finding_id`, `identity_path`, `subject_field`, `marker_field`, `owner_subject_sha256`, `peer_subject_sha256` и `marker_sha256`. Последние три — SHA-256 UTF-8 строк без кавычек и перевода строки. Возьми уникальную случайную метку тестового объекта. В этом профиле обе учётные записи используют Bearer без cookie, поля JSON находятся на верхнем уровне, допуск связи запросов по времени — пять минут. Закрытый эталон использует ту же схему, путь и параметры запроса. Ограничение доступа задаёт спецификация системы. Просмотр чужой общедоступной записи не подходит под этот профиль.

### Сигналы анализаторов

Поддерживаются `semgrep` (check_id), `trivy` (VulnerabilityID), `zap` (pluginid), `testssl` (id с уровнем LOW и выше, flat JSON), `slither` (check), `forge` (имя теста, JSON suite/test_results) и `echidna` (имя свойства со статусом solved). Задай `rule.detector` и приложи отчёт по одному активу или проекту. Для этих правил привязка входного файла к активу задаётся оператором. Такие сигналы остаются гипотезами, даже при повторе.

### Как определяется результат

- `confirmed` требует прямого совпадения, двух независимых сборов цели и чистого контрольного образца. Сборы должны отличаться сборщиком, архивом, источниками записей и временем. Для HTTP проверяются собственный идентификатор снимка ARTEX, SHA-256 и длина тел, заголовки и соответствие сообщения исходным байтам.
- `observed` и `corroborated` различают единичное наблюдение и независимый повтор при неполной проверке. `conflicting` означает несовместимые исходы или срабатывание на эталоне. `not_reproduced` относится к сопоставимым записям цели с чистым контролем.
- `insufficient` означает нехватку данных, `hypothesis` — сигнал сканера. Ошибка целостности в любом заявленном входе даёт `invalid_evidence`. Отбор файлов и полнота журналирования влияют на вывод. Отсутствие записи само по себе не доказывает безопасность.
- Чтобы оценить точность на размеченном корпусе, добавь `--labels truth.json`. Пример разметки: `{"demo-header":{"revision":"fixture-v1","present":true}}`. Готовь её независимо от вывода программы и включай трудные отрицательные случаи. Отчёт показывает TP/FP, precision с интервалом Уилсона, полноту и долю случаев с решением. Воздержания остаются в знаменателе полноты. При отсутствии подтверждений precision остаётся неопределённой.

### Модели

Опция `--models --max-calls 12` включает OpenAI-совместимые профили. В окружении задай `WHITEHAT_STRONG_URL`, `WHITEHAT_STRONG_MODEL`, `WHITEHAT_STRONG_KEY` для GLM и такие же `WHITEHAT_WORKER_*` для Qwen. URL — базовый адрес API, например с суффиксом `/v1`. Ключи можно опустить для локального провайдера. Штатные ключи и БД ARTEX этому процессу не нужны.

GLM распределяет очередь случаев. Qwen выбирает чтение цели, контроля или сверку повторов и оценивает результат. Спорные и неполные случаи получает GLM. Моделям передаются тип проверки, числовой индекс, категории исходов и логические признаки. Свободные команды, адреса активов, заголовки и тела запросов в протокол не входят. Предложение модели сохраняется отдельно от статуса доказанности. Бюджет общий в вызовах, максимальный ответ — 1200 токенов. Коды выхода: 0 — отчёт построен, 1 — ошибка запуска/манифеста, 2 — отчёт построен с ошибкой доказательств, 3 — отчёт построен с неполным разбором моделей.

## Изолированный запуск

В `compose.whitehat.yaml` есть только пакетный обработчик отчётов. Задай `WHITEHAT_PYTHON_IMAGE` с закреплённым digest доверенного образа Python, `WHITEHAT_INPUT` и `WHITEHAT_OUTPUT` абсолютными путями. Каталог вывода должен существовать и быть доступен UID/GID контейнера. Команда `docker compose -f compose.whitehat.yaml run --rm report` читает `case.json` и создаёт новый подкаталог `result`. Сеть контейнера отключена. Для нового отчёта выбери новый каталог вывода.
